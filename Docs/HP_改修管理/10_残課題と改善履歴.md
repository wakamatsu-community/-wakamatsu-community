# 無料枠試算・移行計画・セキュリティ残課題管理書

## 1. 無料枠（Sparkプラン / Google無料枠）の制限と使用量試算

若松町内会（約100〜500世帯）が月額0円で運用し続けるためのリソース試算および制限値一覧。

| サービス | 無料枠の上限（制限値） | 若松町内会の想定月間使用量 | 安全マージン | 判定 |
| :--- | :--- | :--- | :---: | :---: |
| **Firestore 読み取り** | 50,000 回 / 日 (約150万回/月) | 約 30,000〜50,000 回 / 月 (IndexedDBキャッシュ利用) | 約 30倍〜50倍 | **◎ 無料運用成立** |
| **Firestore 書き込み** | 20,000 回 / 日 (約60万回/月) | 約 300〜1,000 回 / 月 (行事・予約・意見) | 約 600倍 | **◎ 無料運用成立** |
| **Firestore 削除** | 20,000 回 / 日 (約60万回/月) | 月間数十件程度 | 圧倒的余裕 | **◎ 無料運用成立** |
| **Firestore 保存容量** | 1 GiB | 約 10〜30 MB (テキスト・メタデータ数万件) | 約 30倍〜100倍 | **◎ 無料運用成立** |
| **Firebase Auth** | 50,000 MAU / 月 (Email/PW, 匿名, Google) | 数十〜数百アカウント | 約 100倍〜500倍 | **◎ 無料運用成立** (※SMS認証は除外) |
| **Google Drive 容量** | 15 GB / アカウント | 写真アルバム・広報PDF で約 2〜5 GB | 約 3倍〜5倍 | **◎ 無料運用成立** (※Storage不使用) |
| **GitHub Pages 帯域** | 100 GB / 月 | 約 3〜5 GB / 月 (静的アセット配信) | 約 20倍 | **◎ 無料運用成立** |
| **GAS 実行枠** | Webアプリ同時接続 30 / トリガー日計 90分 | 同時アクセス数名〜十数名 / トリガー不使用 | 約 3倍〜10倍 | **◎ 無料運用成立** |

### 無料運用（月額0円）の成立条件とルール
1. **「条件付き無料運用」の原則**:
   - 本システムは「永続的な無料保証」や「完全無制限」ではなく、住民規模（50〜200名）および想定利用量が Google / Firebase の無料枠制限内に収まっていることで成立する**条件付き無料運用**である。
   - 今後利用者が急増した場合や、サービス側の規約・無料枠仕様の変更があった場合は再評価が必要となる。
2. **有料化機能の完全排除**:
   - Firebase Spark では Cloud Storage for Firebase は使用せず、無料 15GB の Google Drive に一本化する（クレジットカード登録要求の回避）。
   - 電話番号SMS認証など従量課金が発生する認証方式は採用せず、メール/パスワード、匿名認証、Google OAuth を使用する。
3. **写真のクライアント側自動縮小**:
   - スマホ写真をそのまま送信せず、必ず長辺最大 1200px / JPEG品質 0.8 にブラウザでリサイズしてから保存する（1枚あたり約 200〜400KB に抑制）。
   - 年間 500 枚の写真投稿でも約 150MB 程度となり、15GBの容量に対して10年以上無料枠を維持可能。
4. **Firestore の期間クエリとオフラインキャッシュ**:
   - カレンダーや一覧表示で全件取得（全件スキャン）を避け、`where` 句で対象期間（直近2〜3か月）に限定して読み取り回数を最小化する。
   - `persistentLocalCache`（IndexedDB）により、再訪問者の読み取り回数をほぼゼロにする。
5. **GAS の同時実行・実行時間制限の遵守**:
   - GAS Webアプリは同時実行数 30 接続の制限があるため、写真ギャラリー等で大量同時プロキシ配信を行わず、公開写真はDrive直接配信、機密資料のみGASプロキシとする。
   - GAS のトリガー実行制限（1回6分、日計90分）と Web アプリ実行制限（同時実行数30）を混同せず、長時間の定期トリガー実行は行わない。

## 3. セキュリティ上の残課題と対応策

| 課題項目 | リスク内容 | 対策方針 |
| :--- | :--- | :--- |
| **1. サービスアカウント鍵の漏洩リスク** | `FIREBASE_SERVICE_ACCOUNT` が公開リポジトリやブラウザに混入すると全権限が掌握される。 | `.gitignore` で除外を徹底。GitHub Pages のビルド（`build_pages.py`）では公開用 Config（APIキー等）のみ注入し、サービスアカウント鍵は一切配信しない。 |
| **2. APIキーの公開と不正アクセス** | Firebase APIキーはブラウザに渡るため誰でも閲覧可能。 | APIキーは「プロジェクト特定用」であり、アクセス制御は **Firestore Security Rules** で100%遮断する。未認証の書き込みや権限外操作をDB層で拒絶。 |
| **3. 写真・PDFの直リンク流出** | Google Drive の「リンクを知る全員」共有はURL漏洩時に部外者も閲覧可能。 | 個人情報を含む機密資料・役員会議事録は **Firebase Storage** で認証必須保護にする。写真投稿時は肖像権の確認喚起を行う。 |
| **4. 役員ロールの不正取得** | 会員が自身のロールを勝手に `officer` に書き換えるリスク。 | Security Rules において `users` ドキュメントの `role` フィールド変更権限を「既存の `isOfficer()`」のみに限定。一般会員は自分自身の権限を昇格できない。 |
| **5. 悪意ある大量投稿（スパム）** | 意見交換や写真投稿への連続投稿による無料枠の消費。 | 会員ログインを投稿の必須条件とするか、クライアント側レートリミットおよび Security Rules で短時間の連続書き込みを抑止。 |
